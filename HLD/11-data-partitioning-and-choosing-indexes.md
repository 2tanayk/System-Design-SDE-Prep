# Data Partitioning, Indexes, and Choosing the Right Strategy

## 1. The central rule

**Start with query optimization and indexes. Consider partitioning when the data size, query patterns, or data-retention requirements justify dividing a table into physical partitions.**

Indexes and partitioning solve different problems, and PostgreSQL tables often use both together.

- **Index:** helps PostgreSQL find matching rows without scanning every row.
- **Partitioning:** splits one logical table into smaller physical tables and can let PostgreSQL skip entire partitions.
- **Query optimization:** reduces the amount of work a query performs.
- **Caching:** avoids repeating expensive reads by reusing stored results.
- **Archiving or partition retirement:** manages data that is no longer operationally needed.
- **Replication and sharding:** address other needs, such as read scaling or distributing data across database servers.

Partitioning is not a replacement for indexes. It is also not an automatic performance improvement just because a table has millions of rows.

## 2. Index first: a customer order-history query

Suppose the API needs the latest 20 orders for customer 101.

    SELECT order_id, created_at, status, total_amount
    FROM orders
    WHERE customer_id = 101
    ORDER BY created_at DESC
    LIMIT 20;

A composite index matching the filter and ordering is a reasonable candidate:

    CREATE INDEX idx_orders_customer_date
    ON orders (customer_id, created_at DESC);

PostgreSQL may use this index to locate one customer's orders in date order and stop after finding enough rows. Check the real query plan rather than assuming the index will always be chosen.

Partitioning the same table by month may not help this query much if the query does not specify a date range: PostgreSQL may need to look across multiple monthly partitions to find that customer's latest orders.

**Decision:** for a slow query that filters by a particular column, first inspect the query and plan, then test a suitable index. Do not add partitions as a substitute for a missing index.

## 3. When range partitioning helps

Range partitioning divides the table by ranges of a partition-key value, such as a date. It is a strong candidate when queries commonly include that date range, or when old data can be retired in whole ranges.

For example, a query that asks only for March data can potentially skip every other monthly partition:

    SELECT COUNT(*), SUM(total_amount)
    FROM orders
    WHERE created_at >= DATE '2026-03-01'
      AND created_at <  DATE '2026-04-01';

The skipping of irrelevant partitions is called **partition pruning**. An index inside the March partition may still help when a query selects a small subset of March's rows. For a query reading most rows in that partition, a sequential scan might be more efficient.

### PostgreSQL example: range-partitioned orders

The following is a self-contained learning example. Run it in a development database. It creates a parent table and monthly child partitions.

    DROP TABLE IF EXISTS orders_range CASCADE;

    CREATE TABLE orders_range (
        order_id BIGINT GENERATED BY DEFAULT AS IDENTITY,
        customer_id BIGINT NOT NULL,
        created_at DATE NOT NULL,
        status TEXT NOT NULL
            CHECK (status IN ('PLACED', 'PAID', 'SHIPPED', 'CANCELLED')),
        total_amount NUMERIC(10, 2) NOT NULL CHECK (total_amount >= 0),
        shipping_city TEXT NOT NULL,
        PRIMARY KEY (order_id, created_at)
    ) PARTITION BY RANGE (created_at);

    CREATE TABLE orders_range_2026_01
    PARTITION OF orders_range
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

    CREATE TABLE orders_range_2026_02
    PARTITION OF orders_range
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

    CREATE TABLE orders_range_2026_03
    PARTITION OF orders_range
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

    CREATE INDEX idx_orders_range_customer_date
    ON orders_range (customer_id, created_at);

The lower boundary is inclusive and upper boundary exclusive. For example, February 1 belongs to the February partition. These three partitions only cover January through March 2026; inserts or updates with dates outside those ranges will fail unless another suitable partition or a default partition exists.

### CRUD: insert rows

    INSERT INTO orders_range
        (order_id, customer_id, created_at, status, total_amount, shipping_city)
    VALUES
        (1001, 101, DATE '2026-01-15', 'PLACED', 799.00, 'Mumbai'),
        (1002, 102, DATE '2026-02-01', 'PAID', 1499.00, 'Pune'),
        (1003, 103, DATE '2026-02-28', 'SHIPPED', 499.00, 'Delhi'),
        (1004, 101, DATE '2026-03-01', 'PLACED', 2199.00, 'Mumbai'),
        (1005, 104, DATE '2026-03-17', 'PAID', 899.00, 'Bengaluru');

Insert through the parent table. PostgreSQL routes each row based on created_at.

### CRUD: read rows

    SELECT order_id, customer_id, created_at, status, total_amount
    FROM orders_range
    WHERE created_at >= DATE '2026-02-01'
      AND created_at < DATE '2026-03-01';

This query can prune January and March and scan the February partition. Supplying the partition key is what allows PostgreSQL to identify the relevant range.

To see which physical child table stores each row:

    SELECT tableoid::regclass AS physical_partition,
           order_id, customer_id, created_at, status
    FROM orders_range
    ORDER BY created_at;

### CRUD: update a non-partition key column

    UPDATE orders_range
    SET status = 'SHIPPED'
    WHERE order_id = 1001
      AND created_at = DATE '2026-01-15';

The row remains in the January partition because created_at did not change.

### CRUD: update the partition key

    UPDATE orders_range
    SET created_at = DATE '2026-03-10'
    WHERE order_id = 1002
      AND created_at = DATE '2026-02-01';

The row moves from the February partition to the March partition because its partition-key value changed. PostgreSQL handles the movement. The destination partition must exist and accept the new value.

### CRUD: delete one row

    DELETE FROM orders_range
    WHERE order_id = 1003
      AND created_at = DATE '2026-02-28';

This deletes the row from the relevant partition while leaving the partition itself in place.

For whole-month retention, dropping or detaching a partition can avoid deleting each row individually, but it is a schema/data-lifecycle operation and must be planned carefully.

## 4. When hash partitioning helps

Hash partitioning routes rows by a hash of a key, such as customer_id. The goal is to distribute keys across partitions. It is useful to evaluate when equality lookups by that key are common and a large table benefits from being split into partitions.

Hash partitioning is less helpful for a date-range query if date is not the partition key. That query may need to visit multiple or all hash partitions. A skewed workload or very active customer can still be hot; hash partitioning does not guarantee perfectly even traffic.

### PostgreSQL example: hash-partitioned orders

    DROP TABLE IF EXISTS orders_hash CASCADE;

    CREATE TABLE orders_hash (
        order_id BIGINT GENERATED BY DEFAULT AS IDENTITY,
        customer_id BIGINT NOT NULL,
        created_at DATE NOT NULL,
        status TEXT NOT NULL
            CHECK (status IN ('PLACED', 'PAID', 'SHIPPED', 'CANCELLED')),
        total_amount NUMERIC(10, 2) NOT NULL CHECK (total_amount >= 0),
        shipping_city TEXT NOT NULL,
        PRIMARY KEY (order_id, customer_id)
    ) PARTITION BY HASH (customer_id);

    CREATE TABLE orders_hash_p0
    PARTITION OF orders_hash
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);

    CREATE TABLE orders_hash_p1
    PARTITION OF orders_hash
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);

    CREATE TABLE orders_hash_p2
    PARTITION OF orders_hash
    FOR VALUES WITH (MODULUS 4, REMAINDER 2);

    CREATE TABLE orders_hash_p3
    PARTITION OF orders_hash
    FOR VALUES WITH (MODULUS 4, REMAINDER 3);

    CREATE INDEX idx_orders_hash_customer_date
    ON orders_hash (customer_id, created_at);

The four partitions represent the four possible remainders for modulus 4. PostgreSQL computes the hash and routes the row automatically; application code should not calculate or hardcode the destination partition.

### CRUD: insert rows

    INSERT INTO orders_hash
        (order_id, customer_id, created_at, status, total_amount, shipping_city)
    VALUES
        (2001, 101, DATE '2026-01-15', 'PLACED', 799.00, 'Mumbai'),
        (2002, 102, DATE '2026-02-01', 'PAID', 1499.00, 'Pune'),
        (2003, 103, DATE '2026-02-28', 'SHIPPED', 499.00, 'Delhi'),
        (2004, 101, DATE '2026-03-01', 'PLACED', 2199.00, 'Mumbai'),
        (2005, 104, DATE '2026-03-17', 'PAID', 899.00, 'Bengaluru');

Orders for customer 101 route to the same partition even though their dates differ.

### CRUD: read rows

    SELECT order_id, customer_id, created_at, status, total_amount
    FROM orders_hash
    WHERE customer_id = 101
    ORDER BY created_at;

Because customer_id is the hash key, PostgreSQL can prune partitions that cannot contain that customer. By contrast, a query that filters only by order_id usually cannot determine which partition contains the row.

### CRUD: update a non-partition key column

    UPDATE orders_hash
    SET status = 'SHIPPED'
    WHERE order_id = 2001
      AND customer_id = 101;

The row remains in its current partition because customer_id does not change.

### CRUD: update the partition key

    UPDATE orders_hash
    SET customer_id = 999
    WHERE order_id = 2002
      AND customer_id = 102;

PostgreSQL moves the row to the partition selected by the new customer_id.

### CRUD: delete one row

    DELETE FROM orders_hash
    WHERE order_id = 2003
      AND customer_id = 103;

Delete from the parent table; PostgreSQL locates the relevant partition.

## 5. PostgreSQL primary-key limitation on partitioned tables

A parent-level PRIMARY KEY or UNIQUE constraint on a PostgreSQL partitioned table must include all partition-key columns.

That is why the range example has:

    PRIMARY KEY (order_id, created_at)

And the hash example has:

    PRIMARY KEY (order_id, customer_id)

These composite keys guarantee uniqueness of the pair, not order_id alone. They do not by themselves enforce global uniqueness of order_id across partitions. An identity column generates values from a sequence during normal inserts, but identity generation alone is not a uniqueness constraint if explicit values or other write paths can introduce duplicates.

If global order_id uniqueness is a hard requirement, design for it explicitly. One option is to partition by order_id when that suits the workload. Another is to maintain a separate unpartitioned registry with order_id as its primary key, though that introduces additional write and schema complexity. Do not assume a composite key enforces uniqueness on just its first column.

## 6. Compare strategies by the problem

| Problem | Strategy to evaluate | Why |
|---|---|---|
| Find one customer's latest orders | Composite index on customer_id and created_at | Helps locate and order a customer's rows |
| Query one date range in a huge table | Date index and/or range partitioning | Index finds rows; partition pruning skips date ranges |
| Report reads most rows in a period | Partitioning plus measured scan strategy | A scan of one relevant partition may be cheaper than fetching many rows from an index |
| Repeated expensive reads | Cache or materialized/pre-aggregated results | Avoids repeating work |
| ORM makes many repeated queries | Fix N+1 and fetching strategy | Reduces database round trips |
| Old monthly data must be retired | Range partitioning and partition lifecycle management | Whole partitions can be detached or dropped |
| One database remains overloaded after tuning | Evaluate larger resources, replicas, or sharding | These address capacity or distributed workload concerns |

Other indexing options depend on the workload. For instance, PostgreSQL BRIN indexes can be useful for very large tables when the indexed value correlates with physical row order, while a B-tree is often a better fit for selective equality and range lookups. Neither index type is always the best.

## 7. A practical decision process

1. **Measure first:** identify the slow endpoint/query and inspect latency and database load.
2. **Inspect the plan:** use EXPLAIN (ANALYZE, BUFFERS) on a representative query. ANALYZE executes the query, so be cautious with expensive operations on production.
3. **Reduce unnecessary work:** review joins, selected columns, pagination, ORM N+1 queries, and application-side processing.
4. **Add a workload-matched index:** verify its benefit against the real plan and workload.
5. **Evaluate partitioning:** use it if queries can prune large sections of the data or if partition-level retention and maintenance are valuable.
6. **Measure again:** indexes and partitions add storage, write, and operational costs. Keep them only when they serve a demonstrated requirement.
7. **Scale or distribute when justified:** consider read replicas, more resources, or sharding if tuning a single database is insufficient.

## 8. Interview summary

**An index helps find rows; partitioning helps skip entire sections of a table and manage data by ranges or keys.** I would first measure the workload, optimize queries, and add suitable indexes. I would consider partitioning when query patterns align with the partition key or data-retention operations benefit from managing whole partitions. I would often combine partitioning with indexes and validate the result with PostgreSQL query plans and benchmarks.
